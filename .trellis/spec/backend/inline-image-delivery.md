# 飞书正文图片交付合同

## 1. 范围与触发条件

修改最终回复中的本地图片解析、图文完成卡、正文块媒体快照、待发恢复或图片分块时使用本合同，并遵守 [可靠性合同](./reliability-contracts.md)。原生 Codex imageGeneration 通知的准入规则保持独立，不能从 imageView、savedPath 或工具日志猜测交付产物。

## 2. 接口

- `deliverResponse(..., options?)` 的选项包含 `workingDirectory?: string`、`finalize?: (preparedText: string) => Promise<boolean>`。manager 传入当前绑定的工作目录；finalize 必须使用投递层准备后的正文，不继续捕获原本地路径正文。
- `snapshotInlineImages(text, workingDirectory?, { count, bytes, images? }?)` 返回 `{ text, images }`，只在飞书最终投递准备时读取明确引用的文件。可选 `images` 为已接受的原生图片，用于扣除正文吸收同内容图片后的预算，避免重复计数和重复发送。
- `markdownImageSpans(text)` 返回真实 Markdown 图片节点的范围和 src/alt；`describePendingInlineImages(text)` 在运行态纯转换正文，不访问磁盘。
- `InlineResponseImage` 为 `{ marker: string; image: GeneratedImage; imageKey?: string }`；Markdown 文本块通过 `inlineImages?: InlineResponseImage[]` 关联媒体。初始 marker 为内部图片标记，真实 key 分块后 marker 与已保存 imageKey 相同；恢复校验不能只接受初始标记。旧无 kind 文本与原生独立 image 块仍可加载。

## 3. 数据与行为合同

只处理正文真实 Markdown 图片节点。支持相对路径、Windows 绝对路径、尖括号内含空格路径；代码块、行内代码和普通文字中的路径不触发读取。图片位置替换必须基于解析出的节点范围，不对全文路径做全局替换。

表格单元格的 inline token 没有 map，必须从所属行和单元格的来源范围建立字符映射，并保留表格预处理前的转义。转换应保留原 alt 的有效转义及标题，不重复给方括号、反斜杠加转义；alt/title 或说明中的竖线不能变成表格分隔符。已写入正文的上传 key 不再次重写整个图片节点。

路径按当前绑定工作目录解析，规范化前和 realpath 后都检查边界，拒绝越界、目录及符号链接逃逸。读取长度受限制，复用现有 PNG 结构、尺寸及每图/每轮预算，原生与正文媒体共享回合预算。无效、缺失或不支持的文件以对应位置的文字说明替换；不让客户端加载本机路径，不透传原始文件错误。

保存正文及媒体快照并 await flush 后才能上传；保存 imageKey 并 await flush 后才能用其更新卡片或发送。重复引用复用上传结果并保留每个引用位置。补发使用持久快照与已保存 key，不重新读取路径、不重调模型、不依赖源文件仍存在。

图片标识准备完成后，完成卡收到转换正文。只有平台确认完整正文与内嵌图片对应的内容，才能将正文块标为 sent。上传失败时的正文说明预览不等于完整交付，不能清空其待发材料。原生独立图片仍分别确认；正文吸收的图片不再次独立发送。

上传失败优先用现有 finalize(previewText) 收尾原卡，显示完整正文与图片待补发说明；其成功回执只结束该预览卡，不能确认 outbox。模型回合终态沿用已有 completed/error/interrupted 语义，投递失败另由待补发说明及 /retry 回执呈现。没有原卡或收尾失败时才走说明预览；取消后不新增收尾，等待仍受投递期限约束。

含已转换图片的回复使用支持图片的卡片路径。卡片发送失败不能仅因纯文字降级成功便宣称图文送达。分块以真实上传 key 的最终序列化预算为准，不能拆坏图片语法；重试只发送未确认块。沿用取消、超时、迟到回执与成功进度先保存的可靠性规则。

## 4. 校验与错误矩阵

| 条件 | 必须结果 |
| --- | --- |
| 有效两图正文 | 上传 key 替换两 src，同卡顺序保持 |
| 缺失、坏 PNG、非 PNG、超限、越界或路径逃逸 | 对应位置说明，保留其余正文与已接受图片 |
| 第二张上传失败 | 已保存第一 key 保留，图文未确认，可补发 |
| 上传失败时仍有原过程卡 | 原卡以待补发正文收尾，清理运行态；预览回执不确认待发图文 |
| 同图多处引用 | 上传结果复用，引用位置不丢 |
| 重启且源文件已移走 | 从待发快照继续，不重新读取文件 |
| 卡片失败、纯文本降级成功 | 图文仍失败待补发，不误记 delivered |
| stop/new/bind/停机后上传迟到 | 不自动继续发送，不更新新回合 |
| 超长正文且图片临近边界 | 按封装体积完整分块，图片节点不损坏 |

## 5. 正常、边界与失败示例

- 正常：`说明A\n![预览](<G:/project/demo/a.png>)\n说明B` 在 `G:/project` 会话中转换成同位置的飞书图片标识。
- 基线：纯文本不读取图片文件；无正文引用的原生生成图仍按原文字在前、独立图片在后的流程交付。
- 边界：两个引用指向同一 PNG，保留两处显示位置并复用上传 key。
- 失败：`![图](../outside/private.png)` 位于工作目录之外，只显示读取失败说明，不上传。

## 6. 必需测试断言

合成临时 PNG 与 fake 上传/发送，阻断真实模型和平台网络，每批外层硬超时 60 秒。断言上传前快照 flush、发送前 key flush、finalize 实际参数、同卡 key 与顺序、失败预览不确认、失败原卡终态、真实 JSON store 重建恢复、源文件移走后补发、取消迟到、预算、代码示例不读取、重复引用、卡片失败与图片边界分块。继续跑原生生图、媒体待发及流卡相关回归；表格单元格图片、多个单元格与 alt/title 中的转义竖线须覆盖，转换或说明预览不能破坏表格分列。

真实客户端图片显示必须通过经授权的联调验收；fake 平台成功仅证明请求结构与状态语义，不代表已经验证生产显示。

## 7. 错误与正确做法

- 错：把本机 src 原样放进 Markdown，finalize 返回 true 后把该块算送达。正确：先保存并上传图片，再用 imageKey 转换正文，确认完整图文。
- 错：补发时重新打开模型上次提到的路径，或扫描输出目录寻找图片。正确：只在本轮准备时解析正文明确图片节点，后续复用持久快照。
- 错：卡片发送失败后纯文字 fallback 成功便清除图片材料。正确：保留图文待发状态，让用户补发未确认内容。
