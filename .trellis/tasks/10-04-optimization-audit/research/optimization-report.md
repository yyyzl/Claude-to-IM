# Claude-to-IM 整体优化分析与实施路线

日期：2026-10-04。审查对象为当前工作树，包含上一轮运行时、模型和飞书升级改动。

## 判断

项目有可保留的结构：平台 Adapter、模型 Provider、权限网关、BridgeStore 和独立工作流已经分开。最有价值的下一步是让停止、切换会话、保存、投递和自动修复的结果可预测，再改善飞书操作体验。升级 SDK 能补能力，但不能自动修复这些跨模块行为。

本轮确认的主要问题是具体故障边界，不是笼统的“代码太长”。没有发现足以定为 P0 的证据；P1 表示下一批应优先修复，不表示已确认生产事故。本轮只增加研究文档和隔离复现脚本，未改业务代码、重启服务或调用真实模型/飞书。

## 一、先让停止与切换会话可信

三种实际场景已经用纯内存模型和渠道复现：

1. 发 `//review ...` 等模型透传命令后，接收循环等待整个模型回合。后续 `/stop`、授权和问答不能被消费，其他聊天也受同一渠道影响。
2. 运行中 `/new`，虽然旧任务收到 abort，晚到的旧模型/SDK 会话仍按复用的 binding ID 写回。新会话可能带上旧运行时会话信息。
3. 飞书默认有 1.2 秒消息合并窗口。在窗口内 `/stop` 会回复没有任务，随后消息照样执行；旧串行队列请求也可能在 `/new` 后进入新会话。

源码：[命令分类](G:/project/Claude-to-IM/src/lib/bridge/bridge-manager.ts:954)、[旧回合写回](G:/project/Claude-to-IM/src/lib/bridge/bridge-manager.ts:1461)、[停止入口](G:/project/Claude-to-IM/src/lib/bridge/bridge-manager.ts:1774)。

建议先加一个明确的任务记录：`turnId + sessionId + bindingGeneration + 状态 + 取消句柄`。入队时固定所属会话；执行、写回和更新卡片前检查 generation。停止覆盖合并、排队、运行和等待输入；命令解析只负责判断意图，模型请求全部进入同一个调度入口。

这不要求先重写整个 manager。先修行为和测试，再抽 Scheduler/命令表，避免只把大函数搬到几个文件后保留相同竞态。`stop()` 的 draining、有界取消和迟到回调隔离在同一任务记录上完成。

## 二、让数据损坏可见，让中断的任务可恢复

当前 JSON Store 直接覆盖唯一文件，读取与写入错误都吞掉。损坏文件加载成空状态后，下一次保存只包含新数据；研究 fake 已复现覆盖行为。进程退出也未保证 200 ms 延迟保存已落盘。

工作流虽然有 pause/resume，但真正强杀后遗留的 running 状态会被 resume 拒绝。因此“能继续暂停的任务”和“崩溃后能恢复”目前不是同一件事。

源码：[JSON 读写](G:/project/Claude-to-IM/scripts/claude-to-im-bridge/store.ts:370)、[工作流恢复](G:/project/Claude-to-IM/src/lib/workflow/workflow-engine.ts:204)。

建议先做同目录临时文件写入、原子替换、最后有效备份、flush/close 和可见错误；仅 ENOENT 表示首次运行。工作流增加执行者/租约及检查点版本，确认旧执行者失联后才允许恢复，不能简单放开所有 running。

单进程阶段可以继续用文件。多个进程共享状态、需要事务/历史查询，或合成测试确认保存成本明显影响交互时，再评估 SQLite。没有读取真实历史体积，所以本报告不声称当前已出现性能瓶颈。

## 三、把“生成完成”和“用户收到”分开

当前最终投递返回失败时，manager 仍清理任务并确认入站处理完成。回答往往已经保存在会话里，却没有“待补发”状态。审批提示发送失败更直接：没有卡片和 permission link，模型仍默认等待到超时。

源码：[忽略最终投递结果](G:/project/Claude-to-IM/src/lib/bridge/bridge-manager.ts:1434)、[审批转发](G:/project/Claude-to-IM/src/lib/bridge/permission-broker.ts:121)。

建议保存最小待发记录：正文、turnId、已送分块、失败原因、重试次数。失败后补发既有回答，避免用户重问导致重新调用模型。审批投递失败应结束本次交互并给出原因。用户 `/status` 能看到“模型已完成，回答发送失败”，比只显示空闲有用。

此外已复现 Telegram HTML 降级后遇 429 不继续重试，以及 deliverRendered 失败仍记去重键。后者当前主调用未传 dedupKey，属于接口潜在缺陷，不能夸大为飞书当前的丢信原因。详见专项报告。

## 四、自动修复必须证明自己改的是正确版本

这里值得独立做一批加固：

- 非 HEAD 审查的 diff 来自指定范围，正文 blob 却统一从当前 HEAD 取；模型会拿到不一致的证据。
- 修复 worktree 从执行时 HEAD 建立，没有使用冻结的被审版本。
- 工作区出现任意 diff 就把当前问题记为 fixed；失败组残留还可能被下一组 `git add -A` 一起提交。
- 部分成功时按文件组数量推算 `HEAD~N`，可能生成错误预览。
- 同一 run 重跑会尝试 `worktree remove --force` 和 `branch -D`，可能清掉上次保留给人工检查的成果。

源码：[审查正文取值](G:/project/Claude-to-IM/src/lib/workflow/diff-reader.ts:191)、[修复成功判断](G:/project/Claude-to-IM/src/lib/workflow/auto-fixer.ts:128)、[重跑清理](G:/project/Claude-to-IM/src/lib/workflow/auto-fixer.ts:188)。本轮没有执行真实删除、worktree 或提交。

建议建立不可变的 ReviewBaseline，每次修复单独 attempt，持久化准确 base/head 和提交列表；旧 attempt 默认保留。输出先称“修复候选”，检查目标范围、补丁和相关测试后再标记已验证。移除“最后一个代码块当整文件”的兜底，失败组不能污染下一组。

如果平时主要用 IM 聊天，这项可以和第一批聊天修复并行规划；如果经常使用 review-fix，则应把它放到最前面之一。

## 五、飞书下一步该怎样改善

当前已经用上新版流式卡片和问答表单，不需要再做一次笼统的“迁移新版卡片”。更有收益的是下面几个具体体验：

| 体验 | 改善方式 |
| --- | --- |
| 等待时不知道发生什么 | 同一任务卡显示排队、运行、等批准、等回答、取消中；显示最近活动而非伪造百分比 |
| 授权后卡片还可点击 | broker 确认结果后回写原卡，显示已允许/已拒绝/已过期并移除按钮 |
| 中文长报告样式突然丢失 | 按最终 UTF-8 payload 分段，保留代码和表格结构；长报告用摘要加完整附件 |
| 不知道该选哪个型号 | 从真实运行时目录展示可用模型、思考强度、图片能力；提供显式刷新 |
| 发了 PDF/语音后才知道不支持 | 提前显示桥接支持的附件类型，部分下载失败明确提示，不让用户误以为模型看到了全部附件 |

本轮确认卡片/富文本请求体上限为 30 KB，纯文本为 150 KB。12000 个中文字符可能超过前两者的上限，因此当前 card → post → text 会增加失败请求并退成纯文本，不能简单把“字符限制 30000”当成安全预算。[飞书官方消息限制](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)

已发送审批卡可使用现有 message.patch 更新，官方有效期为发送后 14 天；这类结果回写不要求先建设卡片模板平台。[飞书官方卡片更新](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch.md)

## 六、模型适配、预算和诊断应服务于维护

把 provider 输出收敛为类型化事件，统一终态、用量口径、取消和用户输入请求；Claude/Codex 各自处理厂商协议。新模型能力通过目录和 capabilities 暴露，减少未来每次升级都去改 manager 的次数。

工作流增加总 deadline、最大尝试数和可选用量预算。现有“3 轮 × 每轮最多 3 次 × 90 分钟”仅 Codex 连续超时路径理论上就可等 13.5 小时；这只是代码允许的上界，不是测得的实际延迟。决策步骤临时失败时应复用已有审查产物，不无谓重跑整轮。

诊断优先补 `/doctor` 或本地 `--check`：有效配置来源、运行时版本、连接健康、排队/活跃任务、待发回答和最近错误。默认只读、不启动模型、不记录秘密。进程还活着不代表连接和消息消费正常；fatal 错误也应以正确的退出状态交给监督程序。

测试重点是故障与交错场景；现有单测、typecheck、build 应进入自动检查。性能先用合成数据量测存储写耗时、事件循环延迟、排队时间和卡片请求次数，再决定是否引入数据库或更重组件。

## 建议的增量实施顺序

1. **第一批：行为可靠。** 修生命周期的三个 P1、审批失败、最终送达状态和 JSON 保存/退出 flush；同时为自动修复停止隐式清旧产物、增加基线拒绝保护。验收以本次复现反向变成回归测试为准。
2. **第二批：恢复与可核验结果。** 工作流失联恢复、ReviewBaseline/attempt、修复验证、分块待发记录；再补飞书长回答、审批原卡回写和准确任务状态。
3. **第三批：持续维护。** 类型化 runtime contract、能力/模型选择、只读诊断、总预算、自动检查和负载基准。只有实际需求或测量触发时才做数据库迁移。

每批可以独立验证交付。暂不建议微服务化、引入分布式队列、重做全部 UI、删除所有旧数据，或把提升 effort 当作可靠性修复。
