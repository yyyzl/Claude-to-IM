# 飞书即时追加、去重与文件交付的整合设计

## 边界

父任务负责源需求、四个子任务的顺序和整合验收，不直接作为业务实现目标。即时追加已交付；问答子任务复用该输入及归属合同，区分原问题有效回答与显式迟到补充；去重子任务在最终版本上修改入站接收/调度与 JSON 宿主；文件子任务随后扩展明确产物和现有 outbox。子任务不得同时修改共享的 host.ts、bridge-manager.ts、store.ts 或 response-delivery.ts。尚待用户选择的文件入口只阻塞文件子任务。

## 共用合同

- 平台入站身份、桥接模型 turn 身份和出站记录身份分别保存并可关联；不能以回复文字相同推断同一消息，也不能以入队成功推断执行完成。
- 入站接受/执行状态与出站上传/发送状态分开。模型工作已完成而平台发送失败时沿 /retry 重投已有产物；恢复不另起模型调用。
- 沿用 chat generation、bridge run epoch 和原消息/用户归属。stop/new/bind 及停机后不启动旧任务或继续旧发送。
- 记录由 JSON 宿主负责原子写、校验、备份和 flush；核心仅依赖 host.ts 契约。不引入 SQLite、消息队列服务或全局依赖。
- 文件回传以用户明确指定的本会话产物为依据。原生 imageGeneration 链路保留，普通文件不得靠目录扫描或任意回复路径猜测。
- 异常时保持准确状态：接收失败、执行未完成、执行结果未知、上传失败、平台发送结果未知分别处理；不声称跨系统 exactly-once。
- 即时补充已被模型接收的来源与原回合关联，不能在 finally、后轮队列或去重恢复时再次执行；即时接收未知不自动重送。不得以忙卡仍存在判定模型回合仍活跃。
- RPC 问答原请求有效时答案回原 RPC；原生 async 消息题的答案携原题经既有消息准入。闭合后只能经用户明确动作转换为补充。旧问答不能进入另一 active 回合、其他用户或新绑定。

## 数据流

飞书事件 → 入站状态/准入 → 现有合并、追加及会话队列 → 模型回合 → 响应/文件 outbox → 飞书上传与发送 → 保存已确认进度。

入站状态先由去重子任务建立。文件子任务只复用该接收结果，不另建独立入站去重或执行恢复系统。普通文件传输和文件内容解析分开验收。

## 交付与回退

每个子任务独立功能分支、工作提交和验收，不改写 main 历史。发生缺陷时按子任务工作提交回退代码，不删除用户的历史记录、未送达内容或文件。升级新增记录是可选字段，旧数据不伪造历史处理状态；旧版本回退对新记录的保留边界由各子任务说明。
