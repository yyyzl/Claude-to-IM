# 修复 Codex Fast 能力误判

## 目标与背景
用户在所有 Codex 模型上都看到“不支持 Fast”。用户2026-10-05明确同意“建任务并排查修复”；修复沿用已确认的模型、强度、正常/Fast选择及聊天继承行为，不引入新的产品决策。

本机目录缓存的白名单字段显示10个模型的服务档位为 `{id: priority, name: Fast}`。当前实现四处硬编码 `id === fast`，模拟测试也使用同样错误的ID。上游 rust-v0.160.0 的 TUI按名称忽略大小写识别Fast，开启时发送该目录条目的原始ID，关闭时发送default；app-server原样传递档位ID。本机缓存不等同于真实飞书进程的一次model/list响应，但和源码复现、上游实现交叉吻合。

## 需求
- R1：依据所选模型的serviceTiers识别名称为Fast（忽略大小写）的档位，绝不把展示名称或聊天speed枚举当成请求ID。
- R2：卡片、保存校验、草稿能力检查与运行时采用同一纯函数；聊天仍持久化speed=fast，实际请求发送目录原ID（当前正式例为priority）。
- R3：正常始终传default；保留强度选择、聊天继承和现有失败反馈，不静默切换速度。
- R4：目录无Fast项时不凭模型名猜测可用，也不回退已废弃additionalSpeedTiers；文案只说明目录未提供选项，不断言账号不支持。

## 验收标准
- [x] AC1：priority/Fast的正式数据形状在旧实现复现失败，修复后卡片提供Fast、保存接受且下一轮传priority。
- [x] AC2：Fast名称大小写不敏感；不同原始ID能原样传递；ID叫fast但名称为其他服务时不误认。
- [x] AC3：Fast→正常明确传default；缺失/空目录、不支持组合、刷新失效、账号服务拒绝等已有边界仍通过。
- [x] AC4：相关与全量单元测试（外层60秒）、typecheck/build及独立全范围审查通过。

## 范围外与验证边界
不改全局配置、不读或输出身份/凭据、不升级模型、不调用真实收费请求、不重启生产、不修改会话和卡片安全机制。真实账号Fast授权与飞书客户端渲染仍须与离线证据区分。

## 已解决决策
无待用户决定的产品选项；用户已授权排查修复，按既定交互恢复正确行为。首次研究只采集本机缓存的模型和速度白名单，不复制原缓存。

验收证据：research/quality-check.md；最终648/648离线测试、typecheck/build通过，未进行生产调用或飞书人工渲染。
