# 飞书 Codex 即时追加复用当前卡片

## 目标与用户决定

用户已认可的效果：任务运行中收到文本补充时，将补充交给正在执行的 Codex 回合，继续更新原飞书卡片，最后给出覆盖原问题与补充的答复；不自动创建第二个模型回合及第二张过程卡。模型任务已经结束时，之后的消息按正常新一轮处理。

2026-10-13 用户选择“追加补充当前任务，继续用原卡片”，随后确认“我感觉这个挺好的”。最终范围、结束边界、未知结果处理和 CRITICAL 风险已展示；2026-10-14 用户明确要求“你准备好的话就开始实施呗”，批准该最终方案实施。

## 背景与证据

用户截图对应的实际会话中，22:12:52 与 22:13:10 分别真实执行了一次目录统计，各自输出 46；turn、call、工具及进程 ID 不同。第二轮只收到追加文本。离线调查未复现旧回合事件污染新卡片，22 项相关测试通过。根因是当前追加在第一轮完成后作为独立后轮执行，而不是当前回合输入。

证据详情位于 `.ccg/append-debug/investigation.md`；后续实施依据应优先使用本任务树中的研究记录。当前源码锚点：`bridge-manager.ts:757` 忙时暂存，`:1657` 收尾后排出，`:666` 排出并重新调度，`:1345` 逐轮开启卡片。`codex-llm.ts:191` 恢复线程，`:359` 启动新回合，`:450` 精确隔离回合事件。

## 需求

- **R1 即时文本补充**：首版限定飞书与 Codex、同一聊天和当前任务所有者的普通文本消息，遵循现有追加开关。成功接收后不启动额外 turn/start，不重复调用 onMessageStart，不创建第二张过程卡。
- **R2 真实状态**：只有当前回合确实接收补充后才显示“已追加”；请求处理中或结果不确定时，不把本地暂存伪称模型已接收。
- **R3 生命周期边界**：补充未提交且确认原回合已经结束时，作为正常后续消息执行一次。请求是否接收不明时不得自动再次送入模型，须给出明确结果提示。接收过程中 stop/new/bind 或停机不会把补充送入新任务或更新新卡片。
- **R4 来源与记录**：连续补充按来源顺序提交，模型接收的补充正确进入原会话记录；消息确认跟随真实处理结果。群聊其他发送者、其他会话或其他聊天不得混入原任务。
- **R5 共用能力不退化**：即时输入复用现有文字清理、大小限制及截断审计，不绕过原命令和安全处理。未启用追加、其他平台、Claude 宿主以及带附件消息沿用其现有明确路径，不假报为即时追加。额度查询、审批、会话控制、待发记录及补发不受干扰。
- **R6 内容正确性**：补充影响同一回合的后续工作与最终答复。补充要求重新计算时，新增工具步骤继续显示在原卡；不承诺同一命令永远只执行一次，也不按文本相似度吞掉用户消息。

## 验收

- **A1 → R1/R2**：真实 manager + Codex provider + 内存 JSON-RPC/飞书 transport 验证“第一轮忙时补充”；只有一个模型回合和一张过程卡，turn/steer 输入等于补充内容，接收成功后显示已追加。
- **A2 → R4/R6**：连续两条补充不丢失、不乱序、不重复提交；原会话保存所有补充，最后一份答复覆盖最新要求。新增工具步骤仍在原卡。
- **A3 → R3**：回合未建立、正常活跃、模型已完成但卡片正在收尾、提交后立即完成以及请求结果未知分别覆盖；确认未提交时可进入后轮，结果未知不自动重复执行。
- **A4 → R3/R4**：stop/new/bind/bridge stop 与补充请求并发时，迟到回执不污染新卡片、绑定及记录，不把旧来源迁移到新会话；其他聊天和控制消息继续消费。
- **A5 → R5**：文字控制字符、超长截断及命令输入维持原规则；追加关闭、其他平台/provider、其他发送者及附件路径的既有处理保持明确且可验证；原额度、审批、普通对话、图片与待发补发相关回归通过。
- **A6**：不连接真实模型或生产飞书；每批单测外层硬超时 60 秒；typecheck、build、GitNexus 范围核对及独立审查完成。
