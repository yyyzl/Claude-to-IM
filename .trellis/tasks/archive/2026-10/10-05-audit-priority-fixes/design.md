# 技术设计

## 边界

三个已复现行为缺口，共享一次集成发布和质量门禁。桥接补发与会话列表由同一实现者负责，避免并行修改 manager；工作流恢复单独实现。主会话负责规范、用户文档、提交与归档。既有 PatchApplier 未知标题追加并报告失败的语义保持不变。

## 补发任务生命周期

- 控制消息消费仅登记补发，不等待网络完成；复用管理器的任务跟踪、取消和代际机制。
- 任务捕获 chat/channel、run epoch、绑定 generation，并独立接收取消。重复 `/retry` 仍走既有互斥，不另造发送队列。
- `/stop`、`/new`、`/bind` 和 bridge stop 停止该聊天补发后续分块。已进入平台的发送不能承诺撤回；成功结果仍记入原 outbox，未发块保持可重试。
- 完成回执、异常和 finally 验证归属，不能影响新一代任务；后台承诺必须受跟踪，停机等待有界。

## 当前聊天会话历史

- `/sessions` 数据源从渠道当前 bindings 改为当前 channel/chat 的历史关联。完整 ID 始终可复制并被 `/bind` 接受；支持平台使用现有按钮机制，不新建平台特有卡片协议。
- 将历史关联收束于 host/store 与 router 边界，列表带当前标记、标题、更新时间和工作目录，必要时分页。去重并限制单次列表大小。
- JSON 宿主持久化关联；只导入有确切 channel/chat 证据的当前绑定，不根据标题或任意 sessions 猜测归属。没有历史能力的宿主仅返回当前聊天当前会话，并诚实说明范围。
- 明确切回原会话沿用已有 bind/cancel 流程；列表与按钮不得暴露其他聊天数据。

## 补丁恢复一致性

- 以 round/step 的稳定输入和结果为重放单位，在任何 spec/plan/ledger 变更前持久化足以恢复该决策的数据。
- 使用 WorkflowStore 既有 round artifacts 和版本化读写，避免直接文件 I/O。恢复必须使用同一输入重新确定性计算，或重用已完成结果，不能对已修改的最新文档重新判断成功。
- 固定输出文档版本，避免中断后重复追加新版本；覆盖 spec 已存、plan 已存、ledger 已存、step 未推进的窗口。
- 对已有无法证明稳定输入的半完成旧步骤保守停止并给恢复提示，不默默采用可能已变更的 latest。正常新执行及具有足够历史证据的恢复继续工作。
- 最终设计细节与实际影响图存于 `research/workflow.md`；实现时补充对既有调用点的证据，不能改为放宽失败判定。

## 风险与回滚

- WorkflowEngine.runLoop 为 CRITICAL：start/resume 直接调用，影响 CLI/IM 审查与恢复；已提前向用户说明，必须真实 store + fake 模型故障测试。
- manager 是控制流汇合点，必须覆盖补发、停止、切换、重复重试和停机竞态。
- 所有持久化改动为本项目既有 JSON/artifact 存储；不操作用户现存运行数据。回滚代码时保留新元数据，不删除会话或运行产物。
- 不改变数据库、系统环境或生产服务，不扩大到其他审查建议。
